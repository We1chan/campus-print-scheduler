# 打印店经营管理与多设备协同调度

2026-09-23 根据教师反馈扩展。重点为经营业务、客户等待换优惠、异构设备调度和可复现实验；故障恢复沿用既有机制，作为支撑能力，不再作为主要创新点。

## 运行与演示

```sh
cmake --preset dev
cmake --build --preset dev --parallel 4
./build/dev/bin/campus-print --demo-mode --demo-workload --data-dir runtime/shop-demo                  # 老板后台
./build/dev/bin/campus-print --role student --student 2024000001 --data-dir runtime/shop-demo       # 学生端
```

两个界面是连接同一后台的两个进程，使用相同的 `--data-dir`。老板后台右上角的“打开学生端”会以相同数据目录启动学生端。

Windows 使用 `build/dev/bin/*.exe`。新建经营目录默认六台设备；已有数据目录保留其设备和订单配置，不自动覆盖旧业务记录。默认 GUI 使用应用数据目录的 `shop` 子目录；`--legacy-mode` 默认使用 `queue` 子目录，也可通过 `--data-dir` 显式打开原目录。独立后台用 `print-coordinator --shop-mode --state-dir <目录>`；不带 `--shop-mode` 保留原版同构队列入口。

演示顺序：

1. 新建相同文档，切换快速、普通、灵活，查看价格变化和纸张用量。
2. 提交 A3 彩色双面、A4 黑白、A4 彩色混合订单，设备页观察兼容分配与不同进度。
3. 暂停 A3 设备接单，观察 A3 等待；恢复后自动分配。正在执行的订单不会被接单开关中断。
4. 记录页查看订单规格、锁定报价与交付期限；完成后经营页计入营业额、耗材成本。
5. 经营页补纸；在记录页选中已完成订单，点“退款”并确认，模拟全额退款；重复同额退款不会重复扣款。
6. 经营页点击“运行策略对比”，选择保存位置，查看 21 组结果。完整 JSON 包含输入、配置和每次派发，可复核。

7. 打开学生端：选择文件、调整规格与档位，查看价格和“现在下单”的预计等待，选择支付方式并确认（模拟）。在“我的订单”看顺位、预计完成时间和取件码，在老板后台的记录页与经营页看到同一订单、支付渠道与在线预收。
8. 在老板后台暂停派发或暂停某台设备接单，观察学生端的预计变为“恢复后…”或“兼容设备暂停接单”。

“演示任务”一次提交 24 个混合订单。正常模式也能使用经营功能；demo-mode 额外提供演示任务和原有进程故障按钮。

## 订单、报价和成本

金额均为整数分；下面全部是**模拟定价参数**，不是实际市场价格。

| 项目 | 规则 |
| --- | --- |
| 基础价 | A4 黑白 20 分/打印面，彩色 150 分/打印面；A3 加倍 |
| 快速 | 原价，接受订单后 30 分钟内 |
| 普通 | 95 折，接受订单后 2 小时内 |
| 灵活 | 85 折，接受订单后 8 小时内；当前实现是相对期限，不是日历闭店时间 |
| 打印面 | pages × copies，用于执行进度与计价 |
| 物理纸张 | 单面 pages × copies；双面 ceil(pages/2) × copies，奇数页不能跨份数共用纸张 |
| 纸张成本 | A4 3 分/张，A3 6 分/张 |
| 墨粉估算 | 每面黑白机黑白 5 分、彩色机黑白 7 分、彩色 45 分；A3 加倍 |

服务档位由客户主动选择。后台计算并锁定报价与期限，不接受客户端指定金额。取消和失败不收费；完成后结算一次，累计退款额只能增加且不超过原报价。贡献利润 = 完成订单实收 − 该批订单直接成本，不是扣除租金和人工后的净利润。

当前承诺期限不等于已做过容量保证的预约：系统允许排队、缺纸或临时设备不可用，超时分别列出。尚未实现基于整店未来产能的拒单或预约名额。支付与学号均为模拟（见下文），没有真实支付、账户认证或物理打印机连接。

## 学生端、预计等待与模拟支付

**预计等待。** 后台用当前快照在临时调度器上重放真实的派发规则，得到每个排队订单的预计开始、预计完成和前面的订单数，正在打印的订单按已输出面数估算剩余时间。它随策略、设备能力与接单状态、库存一起变化：没有在线兼容设备或纸张不足的订单显示原因而不是时间；派发暂停时显示“恢复后还要多久”。报价接口同时返回“此刻下单”的预计，学生在付款前就能看到。

预计不是承诺：不含之后到达的订单，也不考虑失败重试和取消；在非 FCFS 策略下，后到订单可能插到前面。承诺仍然只有服务档位的取件期限。演示用的模拟速度很快，预计通常是秒级，不能与 30 分钟 / 2 小时 / 8 小时的期限直接比较。

**模拟支付。** 学生端可选微信、支付宝、校园卡，确认后订单立即入队并记为已支付，不产生任何真实扣款，也没有余额或失败分支。柜台下单记为柜台支付。收入口径不变：完成后才计入营业额；在线已付但未完成的金额单列为“在线预收”；取消或失败的订单不结算，界面显示为原路退款。老板后台按渠道列出实收。

**学号与隐私。** 学号只是订单上的标识，没有登录和校验；填入别人的学号就能看到并取消对方的订单。学生端不显示其他订单的文档名，但本地 IPC 快照本身未做访问控制。“上传文件”只登记文件名、大小和页数：PDF 按页对象或页树计数估算，文本按每页约 50 行，图片按 1 页，其余格式需手动填写；文件内容不保存、不传输、不参与打印模拟。

## 设备与资源

初始配置为三台黑白 A4、两台彩色 A4、一台 A3/A4 全能设备；其中一台黑白设备仅单面。设备名称、能力和黑白/彩色耗时可在空闲时编辑，接单状态可随时调整。耗时为每打印面的模拟毫秒数，A3 加倍；界面明确显示模拟速度。

GUI 默认基准 150 ms/面用于快速演示；实验工具使用默认设备配置的较慢时间尺度。二者必须分别报告，不能把 GUI 墙钟耗时与实验营业日当作相同测量。`defaultFleet` 的基准值限制为 10–1250 ms，倍率为 1–4；单设备每面可配置 10–5000 ms，A3 执行上限 10000 ms。

初始 A4 10000 张、A3 3000 张。第一次领取时预留整单用纸；重试沿用预留；完成后保留消耗，取消或最终失败释放。总补货和完整订单共同形成库存，不另维护容易漂移的可用数。匹配、设备占用检查与库存预留位于同一队列锁内。

这是原子文本输出模拟：未提交输出的失败尝试不消耗物理纸张或墨粉，也不计故障废页成本。剩余工作不计期末在制品成本。不得用这些成本直接声称真实店铺利润。

## 调度策略

三种策略分别定义文档队列排序和打印机分配，共用兼容性、占用和库存约束。订单非抢占执行，先选队列中的文档，再分配设备。

- FCFS：本轮入队顺序；依次寻找编号最小的空闲兼容打印机。
- SJF：打印面数短者优先；分配最快兼容打印机，同速选低成本。
- 综合调度（balanced）：队列使用自研加权响应比，考虑快速/普通/灵活档位、累计等待、期限紧迫度、贡献收益及文档长度，并保护超长等待订单；设备分配尽量保留其他文档唯一可用的设备，再比较速度和成本。

```text
加权响应比 = (1 + 服务分 + 等待分 + 紧迫分 + 收益分) / 打印面数
服务分：快速 32，普通 16，灵活 0
等待分：sqrt(累计排队时间 / 老化间隔)，不封顶
紧迫分封顶 4（已到期时为 0）；收益分封顶 32
累计排队达到 8 小时进入保护组，组内等待最长者先
```

默认老化间隔 30000 ms，累计等待跨重试保留；平方根增长避免等待一项压住其他因素，保护组避免长单和灵活单持续被新单越过。收益使用名义每面贡献，分配设备后才记录实际成本，保持两层职责清晰。完整公式、设备并列规则、迁移和验证见 [两层调度说明](scheduling.md)。旧策略名 priority/deadline/revenue 作为输入别名映射到 balanced，新界面仅展示三种策略。

这是在线启发式；不保证全局最优、持续过载时的履约或理论等待上界。工作台等待列表和预计时间是按当前状态推算的预览，最终分配还依赖实时设备、库存与之后到达的订单，不能当作设备预约表。

## 可复现实验

```sh
./build/dev/bin/shop-experiments --seed 20260923 --customers 600 --hours 8 --output runtime/shop-experiments.json
```

工具先生成同一批潜在客户，保存每人的规格、到达时间、预算分组和等待容忍度，再运行：

1. **固定订单 3 组**：每份订单在各组中的报价、期限相同，只改变 FCFS / SJF / 综合调度策略。
2. **客户选择 18 组**：预算敏感比例 0%、30%、60% × 无优惠/有优惠 × 三种策略。

预算敏感客户的预算是基础价的 90%；其余客户能支付原价。客户在可承受价格且承诺时间不超过容忍度的档位中选择最便宜的，同价选最快。没有优惠时三个档位均为原价。客户不根据真实排队预测选择，不模拟下单后离开，也不因折扣生成额外到达；未下单数只反映给定预算和期限规则。

营业窗口固定 [0, hours]，完成恰好在闭店时计入，闭店时未完成订单无收入，闭店后不再派发。实验使用充足库存、无故障、不自动超时退款。`jobs` 与 `dispatches` 保留全部证据，实际累计退款仍来自显式操作。

利润和营收采用**观察时点的完成订单口径**：窗口内完成订单的总价减其当前累计退款，不是按退款发生日分期的会计现金流。持久界面跨策略切换的历史不构成控制实验；应使用实验工具比较。

### 本地大学文档负载

`shop-experiments --input <workload.json> --hours <1..12> --output <report.json>` 接受 `campus-print-workload` schema 1 的固定订单，比较 FCFS、SJF、综合调度三种策略。每个订单包含 job_id、title、pages、copies、submitted_ms，可带 priority（仅历史元数据）、paper、color、duplex、service；报价和承诺期限仍按生产计价规则计算，输入价格不能覆盖它们。到达必须在观察窗口内，最多 2000 单。此入口不运行模拟顾客选择模型；默认无 `--input` 时仍是 21 组实验。

`tools/run_document_experiments.py` 从本地数据集清单校验全部源文件的大小和 SHA-256，读取 PDF 页树、PPTX 幻灯片清单、Office 保存的分页统计，以及估计表格分页，然后生成三个相同文档集合的固定负载。Word 保存的页数可能过时，表格按每页 45 行 / 8 列估计，其他不能解析的文档用每 16 KiB 一页的明确回退；每项的来源和可信类型都写入 `document-metrics.csv`。页数超过模型上限 1000 时截断并记录。打印选项、到达、优先级和服务档位由源文件哈希确定，均为模拟参数。

依赖：Python 3.10+、`pypdf`；旧 Office 格式读取使用 `xlrd` 与 `olefile`。Codex 内置 Python 已带 pypdf，本次本地补充库放在忽略目录 `runtime/dataset-python`。

```sh
python tools/run_document_experiments.py --dataset datasets/university-life --experiment build/dev/bin/shop-experiments --output runtime/university-strategies-run
```

Windows 给可执行文件补 `.exe`；使用补充库时让本次进程的 `PYTHONPATH` 包含 `runtime/dataset-python`。脚本拒绝覆盖已有输出目录，三个场景各比较三种策略并重复两遍，再独立复核输入不变、派发唯一性、设备兼容、无重叠、等待、利用率、成本及收入。输出保留匿名订单、完整派发、源文档测量清单、哈希证据和摘要。实际文档及全部本地运行记录均放在 Git 忽略目录，CI 的 `document_workload` 只使用自建小型测试文件。

报表增加 `first_started`、`max_first_wait_ms`、`p95_first_wait_ms` 和 `average_observed_wait_ms`。平均首次等待与 P95 只包括已开始的订单；`average_observed_wait_ms` 则对同一集合全部订单计算，仍未开始的等待截止到闭店，因此是窗口内观测值，不是它们最终的完整等待时间。

三策略综合验收另提供 `p95_observed_wait_ms`、`express_on_time_rate`、`contribution_score` 和 `quality_score`，等待、快速履约、贡献收益等权；未开打和未完成订单纳入对应分母，完整公式和 84 组配对验收见 [调度说明](scheduling.md)。`tools/run_scheduling_benchmark.py` 独立从派发记录核算分数，并要求平均综合得分高于 FCFS 与 SJF；原始单项、失败场景和哈希证据全部保留。

客户行为是人为假设，不能用 SDSC 计算日志证明。SDSC 可继续用于原有调度负载研究。新的实验结果必须同时报告营业额、直接成本、完成量、超时和未完成订单，不能只保留收入较高的案例。

## 验证入口

`ctest --preset dev` / `ctest --preset ci` 包括核心计价与匹配、并发库存预留、预计等待（`estimate`，含与回放派发逐项一致的检查）、经营 IPC 全流程（含报价预计、支付字段和 schema 3）、GUI 下单与实验表、学生端上传—支付—取消—取件流程、实验数据复核，以及已有队列回归测试。

`docs/interfaces.md` 是协议契约；经营快照使用持久 schema 3（v0.2 为 2），旧 schema 1 / 2 可继续读取；旧程序会拒绝更新的 schema，防止忽略经营或支付字段后覆盖数据。
